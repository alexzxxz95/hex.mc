# HEX_MC — Scripts Dev Guide

Гайд для авторів **скриптів** — легкий спосіб намалювати власну анімацію на матриці, не пишучи повноцінний модуль і не редагуючи застосунок.

Скрипт — звичайний `.py`-файл, який користувач підвантажує "на льоту" у вбудованому режимі **SCRIPTS** (бічне меню) через вибір папки/файлу. Ніякої пересборки чи встановлення не потрібно.

> Якщо натомість вам потрібен окремий пункт бічного меню зі своєю логікою фонової роботи (push-джерело, слухання системних подій тощо) — це вже рівень **модуля**, див. [MODULES_DEV_GUIDE.md](MODULES_DEV_GUIDE.md).

## Принцип роботи

1. Користувач у режимі **SCRIPTS** обирає папку з `.py`-файлами (або одноразово завантажує один файл кнопкою `[ РАЗОВО ]`).
2. При виборі файлу застосунок імпортує його через `importlib` і викликає, якщо є, `setup_ui(parent)` — один раз, для побудови власної панелі скрипта під бібліотекою файлів.
3. Щокадру (~30 разів на секунду), поки скрипт активний, викликається `update()` — тут генерується кадр.
4. При виході з режиму SCRIPTS або зміні активного файлу скрипт **вивантажується повністю** (свідомо — чужий код не має жити у фоні, поки користувач не в цьому режимі).

## Контракт скрипта

Скрипт — звичайний Python-модуль з (опційно) двома функціями верхнього рівня:

```python
def setup_ui(parent):
    """Опційно. Викликається ОДИН РАЗ одразу після завантаження файлу.
    `parent` — CTkFrame, куди можна напакувати власні віджети
    (слайдери, кнопки тощо) — тими самими бібліотеками, що й модулі:
    customtkinter / tkinter."""

def update():
    """Викликається кожен кадр (~30 fps), поки скрипт активний.
    Повертає numpy.ndarray форми (5, 16, 3), dtype=uint8, BGR —
    або None, якщо кадр змінювати не потрібно (тоді лишається
    попередній кадр без змін)."""
```

Обидві функції необов'язкові окремо, але без `update()` скрипт нічого не намалює.

## Об'єкт `app` (ModuleContext)

Перед виконанням файлу застосунок підставляє в нього глобальну змінну `app` — це той самий `ModuleContext`, яким користуються повноцінні модулі. Доступний усередині і `setup_ui()`, і `update()` як звичайна модульна змінна.

```python
import numpy as np

def update():
    app.log("тік")                 # запис у системний лог
    temp = app.sensor_data.get("temp")   # телеметрія з пристрою
    grid = np.zeros((5, 16, 3), dtype=np.uint8)
    grid[:, :] = (0, 128, 255)      # BGR
    return grid
```

Ключові поля/методи `app`:

| Поле | Опис |
|---|---|
| `app.log(msg: str)` | Пише рядок у системний лог застосунку. |
| `app.sensor_data` | `dict` з останньою телеметрією пристрою: `temp`, `light`, `ax`/`ay`/`az`, `btn_last_event`, `btn_last_time`, `btn_tap_count`. |
| `app.serial_mgr` | Прямий доступ до `SerialManager`, якщо потрібно (зазвичай не потрібен — надсилання кадру бере на себе застосунок). |
| `app.theme` | Поточна палітра кольорів інтерфейсу (`bg`, `accent`, ...) — для стилізації власних віджетів у `setup_ui()`. |
| `app.font_name` | Шрифт інтерфейсу — для узгодженого вигляду власних віджетів. |
| `app.interrupt_display(grid, duration)` | Показати кадр поверх активного режиму на N секунд, незалежно від того, чи скрипт зараз обраний у меню. |

> **Міграція зі старих скриптів (монолітна версія HEX_MC):** раніше скрипт отримував увесь `MatrixApp` під іменем `app`, і виклик логування був `app.log_process(msg)`. У поточній версії `app` — це `ModuleContext`, і метод називається `app.log(msg)`. Решта (`app.sensor_data`, `app.serial_mgr`) не змінилась.

## Формат кадру

- `numpy.ndarray`, форма `(5, 16, 3)`, `dtype=np.uint8`, порядок каналів **BGR** (як в OpenCV — якщо звикли до RGB, не переплутайте канали).
- Фізична матриця: 5 рядків по 15/16/15/16/15 гексагонів (77 світлодіодів). У 15-довгих рядках стовпець `0` не відповідає реальному пікселю — для точних геометричних візерунків орієнтуйтесь на стовпці `1..15` у таких рядках; для суцільної заливки чи простих ефектів це не критично.
- Можна повертати новий масив або мутувати й повернути перевикористаний — обидва варіанти коректні.

## Мінімальний скрипт

```python
import numpy as np

def update():
    grid = np.zeros((5, 16, 3), dtype=np.uint8)
    grid[:, :] = (255, 0, 0)   # BGR — суцільно синій
    return grid
```

Збережіть як `blue.py` у будь-якій папці, оберіть цю папку в режимі SCRIPTS застосунку — файл одразу з'явиться в списку.

## Повний шаблон з UI та телеметрією

```python
"""
Приклад скрипта HEX_MC: слайдер яскравості + реакція на температуру
з телеметрії пристрою.
"""
import numpy as np
import customtkinter as ctk

_brightness_var = None   # тримаємо посилання, щоб не загубив збирач сміття

def setup_ui(parent):
    global _brightness_var
    label = ctk.CTkLabel(parent, text="BRIGHTNESS")
    label.pack(anchor="w", padx=10, pady=(10, 0))

    _brightness_var = ctk.DoubleVar(value=1.0)
    slider = ctk.CTkSlider(parent, from_=0.1, to=2.0, variable=_brightness_var)
    slider.pack(fill="x", padx=10, pady=(0, 10))

def update():
    gain = _brightness_var.get() if _brightness_var else 1.0
    temp = app.sensor_data.get("temp")

    grid = np.zeros((5, 16, 3), dtype=np.uint8)
    base_color = np.array([40, 40, 220], dtype=np.float32)   # BGR
    if temp is not None and temp > 30:
        base_color = np.array([40, 100, 255], dtype=np.float32)   # тепліший при нагріві

    grid[:, :] = np.clip(base_color * gain, 0, 255).astype(np.uint8)
    return grid
```

`setup_ui()` викликається один раз при завантаженні файлу — панель, яку ви туди напакуєте, лишається видимою, поки скрипт активний, і зникає при вивантаженні (зміна файлу / вихід з режиму SCRIPTS).

## Життєвий цикл і обмеження

- `update()` викликається із загального відеопотоку застосунку (~30 fps, той самий цикл, що й для pull-модулів). Уникайте довгих блокуючих операцій усередині — файлову I/O, мережеві запити, `time.sleep()` — вони гальмуватимуть весь рендер, не лише ваш скрипт.
- Якщо потрібна фонова робота з непередбачуваним таймінгом (мережа, зовнішній процес) — запускайте власний `threading.Thread` із `setup_ui()`, а в `update()` лише читайте вже готовий результат із розділюваної змінної.
- Виняток у `update()` не валить застосунок: помилка ловиться, пишеться в лог (`SCRIPT_RUNTIME_ERR`), і скрипт автоматично вивантажується — доведеться обрати файл заново після виправлення.
- Скрипт повністю вивантажується при виході з режиму SCRIPTS — не покладайтесь на збереження стану між активаціями (окрім як через власне читання/запис файлів, якщо це справді потрібно).

## Безпека

Режим SCRIPTS виконує довільний Python-код **без жодної пісочниці** — скрипт має ті самі права, що й сам застосунок. Тому в інтерфейсі показується попередження:

> ⚠ ЗАВАНТАЖУЙТЕ ЛИШЕ СКРИПТИ З ДОВІРЕНИХ ДЖЕРЕЛ

Якщо публікуєте свій скрипт для інших — вказуйте явно, що він робить, і уникайте прихованих мережевих запитів чи звернень до файлової системи поза очевидною логікою анімації.

## Контрольний список перед публікацією скрипта

- [ ] `update()` не блокує (жодного `time.sleep()`, синхронних мережевих запитів, важкої I/O).
- [ ] Повертається масив саме форми `(5, 16, 3)` типу `uint8` (або `None`, якщо кадр без змін).
- [ ] Кольори в порядку **BGR**, не RGB.
- [ ] `setup_ui()` не кидає виняток при відсутньому `parent` — тестуйте на реальному запуску.
- [ ] Використовується `app.log(...)`, а не застарілий `app.log_process(...)`.
- [ ] Якщо є фоновий потік — він не залишається "висіти" після вивантаження скрипта (скрипт про завершення потоку не отримує явного колбека, тож орієнтуйтесь на прапорці/таймаути всередині власного потоку).
